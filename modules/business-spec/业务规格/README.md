# 业务规格（业务规则唯一权威来源）

本目录下所有 `*.md` 是**业务规则的权威来源**。当业务规格与代码不一致时，**以业务规格为准**，
并且必须识别、报告不一致处 —— 不允许以"当前代码如此"为由自动覆盖规格（见项目根 `AGENTS.md`）。

> 由「业务规格模式」模板 v1 生成于 {{YYYY-MM-DD}}。`_样例-库存管理/` 是格式样例，**照搬前必须替换成真实业务**。

## 二、域内文件约定

```
业务规格/{{域}}/
├─ 00-域索引.md                ← 必需：域职责、文件清单、不一致清单、变更记录
├─ {{单据或能力}}-业务规格.md    ← 一份规格 = 一个可独立验收的业务能力
└─ ...
```

| 约定 | 要求 | 谁来管 |
|---|---|---|
| 域索引 | 每个域必须有 `00-域索引.md`，内含域职责、文件清单、不一致清单、变更记录 | `工具/check-spec-docs.ts` 判 **FAIL** |
| 文件粒度 | 一份规格文件对应**一个可独立验收的业务能力**：一张单据、一条流程、一本台账。不要写成"整个域一大篇" | 靠评审，无自动判据 |
| 文件名 | `{{单据/能力名}}-业务规格.md`。中文名词用业务里的叫法，不造词；一份文件只写一个能力 | `check-spec-docs.ts` 判 **WARN**（见下） |
| 登记 | 每份规格文件必须出现在本域 `00-域索引.md` 的「文件清单」里 | `check-spec-docs.ts` 判 **WARN** |
| 规则编号 | 域内规则编号 `R-{{域简称}}-NNN` 连续，改动只增不删号（作废标注"已作废，被 R-xx 取代"） | 靠评审，无自动判据 |
| 交叉引用 | 跨域引用写清 `业务规格/{{其它域}}/{{文件}}.md#R-xxx` | 靠评审，无自动判据 |

### 2.1 命名与登记这两条是**本模块的约定**（不是待定项）

- 判据在 `工具/check-spec-docs.ts` 第 7 项：域内 `*.md`（`00-域索引.md`、`README.md` 除外）必须以 `-业务规格.md` 结尾，且文件名要出现在该域 `00-域索引.md` 里。
- 两条都只报 **WARN、不阻塞**：脚手架刚生成时域内还没有规格文件，此时不报；有文件但不合规才提示。
- **确实要偏离时**：目标项目已有既定命名（例如沿用公司文档模板名）→ 在域 `00-域索引.md` 里写明"本域沿用 XX 命名，忽略命名 WARN"，并同步改这里的约定，两处一起改。**不要**为了让检查变绿去改文件名而不改约定。

## 三、一份业务规格必须写全的 8 段

1. **适用场景与目标业务行为** —— 这份规格管什么、目标行为是什么
2. **单据与字段口径** —— 字段 / 含义 / 来源 / 校验，含必填与默认值
3. **状态机** —— 状态集 + 允许流转 + 触发动作 + 所需权限
4. **业务规则** —— 编号条目，可被代码与测试逐条引用
5. **校验与异常** —— 触发条件、错误提示、错误码
6. **权限与可见性** —— 谁能看、谁能改、数据范围
7. **联动与接口** —— 与哪些域交互、触发什么、依赖什么
8. **验收场景** —— Given/When/Then，可直接转成测试用例

---

## 四、写规格的纪律（最容易违反的四条）

1. **只写"业务应该怎样"，不写"代码现在怎样"**。规格是目标，不是现状快照。
2. **不从现有代码反推规则**。规格来源 = 需求 / 业务口述 / 现场确认；从代码反推出的内容只能进下文的「不一致清单」等裁决。
3. **找不到规格文件时，只能分析并提出方案，不能自行创造业务规则**（本项目最高优先级纪律）。
4. **禁止为了通过测试而修改业务规则** —— 测试挂了要么改代码，要么说明规格有问题并走确认，不许偷偷放宽规格。
