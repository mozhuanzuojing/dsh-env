# 业务规格模式 · 可移植模板

从一个真实小项目（离散制造业 ERP）的 `AGENTS.md` 规范 + `业务规格/` 目录形态提炼出的**可移植脚手架**。
落到任意项目后，目标项目就具备一条硬约束：**AI 改代码前必须先读业务规格，业务规则不许现编。**

> 模板版本 v1 · 生成日期 2026-09-24 · 适用于任何"有真实业务规则、AI 会反复改代码"的项目

---

## 一、这套模式的三条内核（只搬目录不搬这三条 = 白搬）

| # | 内核 | 落点 |
|---|---|---|
| 1 | **业务规格是业务规则的唯一权威**，优先级高于代码，也高于所有技术文档 | 项目根 `业务规格/` + AGENTS.md「文档优先级」 |
| 2 | **四份核心文档分工固定**，各写各的，不许互相代替 | `AGENTS.md` / `BLUEPRINT.md` / `DECISIONS.md` / `WORKFLOW.md` |
| 3 | **改前 4 条 + 改后 5 检 + 严禁 5 条**写进 AGENTS.md，才真正生效 | AGENTS.md「AI 工作原则（最高优先级）」 |

**最容易漏掉的纪律**（比目录结构重要得多）：

- 代码与规格冲突时 → **必须识别并报告**，不得以"当前代码如此"自动覆盖规格；冲突未解决前，不得继续扩展依赖该冲突的功能。
- **禁止为了通过测试而修改业务规则。**
- 找不到对应的业务规格文件时 → **只能分析并提出方案，不能自行创造业务规则。**

## 三、5 步落到目标项目

**第 1 步 · 裁剪业务域**（决定成败，见第四节）
列出目标项目的**业务链**：谁下什么单 → 谁审 → 谁执行 → 谁记账，逐个归到域里。

**第 2 步 · 生成骨架**
```powershell
node 工具/apply-template.ts --target "D:\path\to\目标项目" --domains "销售管理,采购管理,库存管理,生产管理,质量管理,财务管理,PMC规划,报表管理"
```
默认保留 4 个横向支撑域（`通用` `基础数据` `技术架构` `权限管理`），纵向域由 `--domains` 指定；已存在的文件不会被覆盖（加 `--force` 才覆盖）。

**第 3 步 · 填 AGENTS.md**
- 技术栈与关键命令（语法检查 / 导入检查 / 路由注册 / 迁移 / 翻译同步 —— 按实际栈改，见 AGENTS.md.template 末尾的替换表）
- **模块成熟度表**：把模块逐个填进去，状态是"模块实际状态"的唯一权威
- 把"已稳定且经端到端验证"的模块标出来 —— 它们进入受保护名单

**第 4 步 · 落四份文档正文**
`业务规格/` 先只写域索引；BLUEPRINT 写目标架构；DECISIONS 从 D001 起；WORKFLOW 画主链。

**第 5 步 · 写业务规格 + 验收**
- 规格内容来源 = **需求 / 业务口述 / 现场确认**，**不许从现有代码反推**（反推出来的东西进"不一致清单"，交人裁决）
- 收尾跑体检：`node 工具/check-spec-docs.ts --target "D:\path\to\目标项目"`
- 端到端验收：任选一域走「读规格 → 改一处代码 → 改后 5 检」，并抽查 2 处规格/代码冲突是否被如实报告

## 四、业务域怎么裁剪

### 4.1 横向支撑域（默认保留，一般不用动）

| 域 | 装什么 |
|---|---|
| `通用` | 跨域共用：公共字段口径、全局错误码、通知/待办、打印导出 |
| `基础数据` | 主数据：物料、客户、供应商、仓库、部门、人员、计量单位 |
| `技术架构` | 分层约定、目录结构、鉴权/租户、集成对接口径 |
| `权限管理` | 角色、数据范围、单据级权限、审批权限 |

### 4.2 纵向业务域（按目标项目替换）

裁剪方法三步：

1. **列全单据/台账**：把项目里所有会流转的单据、台账、报表列成一张清单。
2. **按"业务链相邻"归并**：同一条业务链上下游归一个域；归不进业务链的（分析类）归 `报表管理`。
3. **每个域必须能一句话说清职责**：说不清就说明切错了，合并或拆开。

参考的两套现成切法：

| 场景 | 纵向域 |
|---|---|
| 离散制造（本模板的提炼来源，12 域） | `销售管理` `采购管理` `库存管理` `生产管理` `PMC规划` `质量管理` `财务管理` `报表管理` |
| 商贸/进销存（轻量） | `销售管理` `采购管理` `库存管理` `财务结算` `报表管理` |
| 项目型/服务型 | `商机合同` `项目交付` `工时成本` `开票收款` `报表管理` |

**裁剪红线**：域一旦定下，`业务规格/` 下的目录名就是引用锚点（AGENTS.md 成熟度表、WORKFLOW 模块联动表都指向它）。**定好后再改域名的代价是全局替换**，所以第 1 步宁可多花 20 分钟。

## 五、与既有文档体系的关系（避免重复造）

| 目标项目已有 | 本模板怎么摆 |
|---|---|
| 已有 `openspec/` | `业务规格/` 当 specs 层（写"业务应该怎样"），openspec 只管变更流程；不要两边都写同一份规则 |
| 已有 ADR 目录 | `DECISIONS.md` 当收敛索引，正文留在 ADR 文件里，只在 DECISIONS 登记编号与结论 |
| 已有 `CLAUDE.md` / 其他 agent 规范 | AGENTS.md 写业务与技术规范，CLAUDE.md 只留一行"读 AGENTS.md"，避免两份规则漂移 |
| 什么都没有 | 直接落本模板，四份文档 + 业务规格就是全套 |

---

## 六、这份模板**不**解决什么

- 不生成业务内容本身 —— 规格正文必须由懂业务的人给，模板只保证"位置对、格式齐、纪律在场"。
- 不是流程引擎，不带审批流实现，不替代需求管理工具。
- 不保证 AI 一定遵守 —— 纪律靠 AGENTS.md 被每轮会话加载；若目标项目没有指令加载机制，需要额外把 AGENTS.md 挂进该 agent 的规则入口。
